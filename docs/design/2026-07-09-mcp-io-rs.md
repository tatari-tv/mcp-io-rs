# Design Document: mcp-io-rs

**Author:** Scott Idler
**Date:** 2026-07-09
**Status:** Implemented (all phases shipped). Shipped in: mcp-io-rs v0.1.0 (library, Phases 0-3/5/6), v0.1.1 (mcp_io! bin= override), slack-cli v0.1.3 (Phase 4, first consumer).
**Review Passes Completed:** 5/5

## Summary

- `mcp-io-rs` is a shared Rust library that gives any Tatari CLI a local stdio MCP server through one `mcp` subcommand, the same way `renew` gives a CLI its `update` subcommand.
- The host supplies its own rmcp `ServerHandler` (its tools). The library owns the scaffolding: the `mcp` subcommand surface, stdio + logging discipline, self-registration into Claude config, and a `.mcpb` bundle.
- First consumer: `slack-cli`. A matched `mcp-io-py` sibling comes later (Rust-first, on purpose).

## Problem Statement

### Background

Four in-house MCP servers exist today. They all do it differently.

| Tool | Shape | rmcp | Transport | Register | Auth | Tools |
|---|---|---|---|---|---|---|
| oracle (`sb`) | `sb oracle serve` subcmd | 1.3.0 | stdio | project `.mcp.json` (checked in) | none (local) | 19 |
| clyde | `clyde session serve` subcmd | 1.7.0 | stdio | manual `claude mcp add -s user` | none (local) | 5 |
| persona-cli | `persona mcp` subcmd | 2.1.0 | stdio | manual `claude mcp add -s user` | okta-auth-rs, per-user, noninteractive | 16 |
| persona-mcp | separate Python svc | fastmcp | streamable-http (remote, k8s) | Docker + manual add | edge | 14 |
| marquee | crate mounted in server | 1.8.0 | streamable-http (remote) | remote connector + OAuth | Okta OAuth (RFC 9728) | 6 |

- Reference patterns already in the fleet:
  - `renew` -> lib-only crate, git dep by tag, hands the host a `clap::Args` struct + `run(&Renew) -> i32` + a `renew!()` macro that captures the CONSUMER's `CARGO_PKG_*` / `GIT_DESCRIBE` at compile time. Wired via an early intercept in `main.rs`.
  - `okta-auth-rs` | `okta-auth-py` -> matched-name pair, symmetric modules, ONE shared on-disk contract (`tokens.json`). The contract was prose-only and the two DRIFTED: cache path diverged, py lacks features, py is untagged. Lesson carried into this doc: encode the shared contract as a CHECKED artifact, not prose.

- Every Rust stdio MCP in the fleet re-derives the same scaffolding by hand, inconsistently:
  - stdout-is-the-protocol discipline (logging force-routed to a file, `#![deny(clippy::print_stdout)]`).
  - the `ServerInfo` name gotcha: rmcp's `Implementation::from_build_env()` expands `env!("CARGO_CRATE_NAME")` INSIDE rmcp, so every server reports itself as `"rmcp"` unless the host sets `.with_server_info(...)` explicitly (`persona-cli/src/mcp.rs:843-848`).
  - a transport-less `dispatch`/`call` path parallel to `serve` (oracle's `sb oracle call`).
  - the lifecycle boilerplate: `serve((stdin, stdout)).await` -> `service.waiting().await`.

### Problem

- A new CLI that wants a local MCP re-implements all of the above from scratch, differently each time, on a different rmcp version.
- Users hand-run `claude mcp add ...`. Nobody self-installs. There is no `.mcpb` bundle anywhere, so Claude Desktop / Cowork install is fully manual.
- `slack-cli` needs a local MCP now, and it has NO async surface yet (`reqwest::blocking`, sync `main`). Building the scaffolding inside slack-cli would be the fifth divergent copy.

### Goals

- One library. One `mcp` subcommand shape across the fleet.
- Host provides ONLY its tools (an rmcp `ServerHandler`); the library provides everything else.
- Self-register into Claude config (Claude Code user + project, and Claude Desktop), and produce a `.mcpb` bundle for Claude Desktop / Cowork.
- Converge the fleet's local-stdio pattern onto one dependency, one rmcp version, one set of house disciplines baked in.

### Non-Goals

- Remote HTTP transport (streamable-http / SSE). marquee and persona-mcp keep their own remote surfaces. Parked, revisit condition: a second CLI needs a hosted MCP AND wants to share this code.
- MCP resources or prompts. The whole fleet is tools-only; this library is tools-only. Parked, revisit condition: a consumer has a concrete resource/prompt need.
- Replacing persona-mcp (the SRE-owned remote Python service). Out of scope entirely.
- The `mcp-io-py` port. Later. Revisit condition: a second Python consumer appears. The contract artifact (Phase 6) exists so the port cannot drift the way okta-auth did.
- Token / auth management. The host owns its auth (slack-cli via valet + okta-auth). The library never handles a token; a missing token surfaces as a recoverable per-call tool error, and the host may add its own pre-runtime "run `<bin> login`" hint.
- Migrating oracle / clyde / persona-cli onto this library in this doc. This doc ships the library + slack-cli as the first consumer. Fleet migration is a follow-on per repo, tracked but not built here.

## Proposed Solution

### Overview

- New repo `tatari-tv/mcp-io-rs`, one library crate `mcp-io` (no binary). Private, consumed by git dep + tag, exactly like `renew` and `okta-auth-rs`.
- The host CLI:
  1. adds `mcp-io` as a git dep pinned to a tag;
  2. embeds the library's clap type as one variant of its `Command` enum: `Mcp(mcp_io::McpCmd)`;
  3. writes its own rmcp `ServerHandler` (the `#[tool_router]` impl wired to its API) and hands the library a way to build one;
  4. dispatches the `Mcp` arm to `McpCmd::run(...)`.

### Architecture

- The value split, stated plainly:
  - `renew` owns its WHOLE feature because "update" is generic.
  - MCP TOOLS are host-specific (slack's `search_messages`, oracle's `knowledge_search`). The library CANNOT own them.
  - So `mcp-io` owns the SCAFFOLDING; the host owns the `ServerHandler`. The seam is a generic `serve<H: ServerHandler>` plus a clap type the host embeds.

- Because the host's `ServerHandler::get_info` owns the server name, instructions, and capabilities, the host owns its MCP identity. The library never sets the server name (it would report `mcp-io` or `rmcp`). The library docs make the host set `.with_server_info(Implementation::new("<bin>", ...))` explicitly, and Phase 0 proves the seam.

- Module layout (`mcp-io`, Rust 2018+ style, single-word files):

```
src/
  lib.rs        # re-exports: McpCmd, serve, McpIo, Error, Result, mcp_io! macro
  cmd.rs        # McpCmd (clap Args) + McpSub (serve|register|unregister|status|bundle) + run()
  serve.rs      # generic serve<H: ServerHandler>; stdio lifecycle; logging discipline helper
  config.rs     # McpIo config object; bin name/version capture; XDG helpers
  register/
    mod.rs      # register/unregister/status orchestration; target selection
    claude.rs   # Claude Code user + project: delegate to `claude mcp add-json` (opaque-safe)
    desktop.rs  # Claude Desktop config: direct Value-preserving atomic write (macOS; Linux community build)
  bundle.rs     # .mcpb manifest.json generation + packaging
  error.rs      # thiserror Error enum
```

### Data Model

- The registration entry (the `mcpServers` map value) is TARGET-SPECIFIC, not one fixed shape. Verified against real state: Claude Code entries carry `"type":"stdio"` (`~/.claude.json`, and Scott's `manifest.yml:61`); a checked project `.mcp.json` (second-brain) omits `type` and `env`. So the exact per-target shape is NOT committed here; it is pinned by golden fixtures in Phase 3 and reproduced from a real `claude mcp add-json` invocation. Illustrative Claude Code entry:

```json
{
  "mcpServers": {
    "<server-key>": { "type": "stdio", "command": "<abs path to host binary>", "args": ["mcp", "serve"] }
  }
}
```

- `<server-key>` defaults to the host bin name (`slack`). `command` is the resolved absolute path to the running binary (`std::env::current_exe()`), so registration points at THIS build, not a `$PATH` guess.
- No `env` seam in v0.1: slack reads its own XDG config, not env. `env` is omitted from the entry. Seam deferred until a consumer needs it (write-as-if-more-coming, implement-one).
- `~/.claude.json` is the user's ENTIRE global Claude Code state, not just `mcpServers`. Every writer preserves ALL unrelated keys (see Phase 3). Register targets:

| target | path | mechanism |
|---|---|---|
| `user` | Claude Code user scope (`~/.claude.json`, honor `$CLAUDE_CONFIG_DIR`) | delegate to `claude mcp add-json ... -s user` (opaque-safe, idempotent, in-house proven) |
| `project` | Claude Code project scope (`./.mcp.json`) | delegate to `claude mcp add-json ... -s project` |
| `desktop` | macOS `~/Library/Application Support/Claude/claude_desktop_config.json`; Linux community `~/.config/Claude/claude_desktop_config.json` | direct Value-preserving atomic write (no `claude` CLI in Desktop-only installs) |

- `McpIo` config object (built by the `mcp_io!()` macro at the host's call site, mirroring `renew!()`):

```rust
pub struct McpIo {
    server_key: String,   // default: bin name; override via mcp_io!(key = "...")
    bin: String,          // host binary name (for messages/log path)
    version: String,      // host version (CARGO_PKG_VERSION at host call site)
}
```

### API Design

- The clap type the host embeds (shape mirrors `renew::UpdateCmd`):

```rust
#[derive(clap::Args, Debug)]
pub struct McpCmd { #[command(subcommand)] cmd: McpSub }

#[derive(clap::Subcommand, Debug)]
enum McpSub {
    Serve,
    Register   { #[arg(long, value_enum, default_value = "user")] target: Target },
    Unregister { #[arg(long, value_enum, default_value = "user")] target: Target },
    Status,
    Bundle     { #[arg(long)] out: Option<PathBuf> },
}
```

- The dispatch entry point the host calls. The host passes a CLOSURE that builds its `ServerHandler`, so the library controls WHEN construction happens without knowing the concrete type. The closure error is generic (`E: Display`) so the library does NOT bake `eyre` into its public API (the lib is `thiserror` internally; the host stays `eyre`):

```rust
impl McpCmd {
    /// `build` constructs the host's ServerHandler. Called for serve, bundle, AND
    /// status (status builds it to read `get_info().server_info.name` for the
    /// name-mismatch warning; a build failure there degrades gracefully). register
    /// and unregister never build it. The closure MUST be token-free (the slack
    /// handler owns a cloned Config), so no verb requires a login.
    /// Returns a process exit code; the host `std::process::exit`s it (renew's contract).
    pub fn run<H, F, E>(&self, io: &McpIo, build: F) -> i32
    where
        H: rmcp::ServerHandler + Send + 'static,
        F: FnOnce() -> Result<H, E>,
        E: std::fmt::Display;
}
```

- Host wiring (slack-cli), both call sites, mirroring renew's `main.rs` intercept:

```rust
// in Command enum:  Mcp(mcp_io::McpCmd)
if let Command::Mcp(cmd) = &cli.command {
    // slack-cli's crate is `slack-cli` but its binary is `slack`; override `bin` so the log
    // path and the `status` name-check agree with the handler's advertised "slack" name.
    // `server_key` defaults to `bin`. (v0.1.1+; before that a host used McpIo::new directly.)
    let io = mcp_io::mcp_io!(bin = "slack");
    // build is token-free; the handler OWNS a cloned Config (Config: Clone) so H: 'static holds.
    std::process::exit(cmd.run(&io, || Ok::<_, std::convert::Infallible>(SlackMcpServer::new(config.clone()))));
}
```

- The generic serve seam the library owns:

```rust
pub async fn serve<H: ServerHandler + Send + 'static>(handler: H) -> Result<()>;
```

- The library never probes tokens (it is generic over `H` and has no probe method). If a host wants a fail-fast "run `<bin> login`" hint, the host probes BEFORE calling `run()` (persona does exactly this in `main.rs` before building the runtime). A missing/expired token otherwise surfaces as a recoverable per-call tool error.

- The macro the host uses at BOTH call sites (capturing the host's compile-time env, per renew's proven trick):

```rust
let io = mcp_io!();                            // server_key = bin = CARGO_PKG_NAME
let io = mcp_io!(key = "slack");               // override the registration server key only
let io = mcp_io!(bin = "slack");               // override the binary name; server_key defaults to bin
let io = mcp_io!(key = "slack", bin = "slack"); // override both (either order)
```

- `bin` is overridable because a host's crate name and its installed binary can differ (slack-cli's crate is `slack-cli` but its binary is `slack`), and `bin` drives the log path and the `status` name-check. This mirrors `renew!(bin = "...")`. Without it a consumer must fall back to `McpIo::new(...)` directly; the macro is the intended seam, so it covers the `bin` override rather than forcing that fallback. (Added in v0.1.1.)

### Implementation Plan

#### Phase 0: Prove the generic serve seam (spike, throwaway)
**Model:** opus
- Zero product code. In `mcp-io`'s `examples/`, define a dummy 1-tool `ServerHandler` and prove a generic `serve<H: ServerHandler>(handler)` compiles and handshakes with a real MCP client (the MCP Inspector or `claude mcp`), listing the dummy tool. This de-risks the one foundational seam the whole library rests on (generic-over-host serve on rmcp 2.1.0).
- **Success criteria:**
  - `cargo run --example spike` serves over stdio; an MCP client lists exactly the dummy tool;
  - if generic `serve<H>` does not compile/handshake against rmcp 2.1.0, that is discovered HERE before anything is built on it.

#### Phase 1: Scaffold the crate
**Model:** sonnet
- Init the `mcp-io` lib crate (house lib conventions: `thiserror`, crate-level `#![deny(...)]` lints, `#![deny(clippy::print_stdout)]`). All deps via `cargo add` (rmcp 2.1.0, tokio, schemars, serde/serde_json, clap, dirs, eyre in examples only).
- Land `McpCmd` / `McpSub` (clap), the `McpIo` config object, the `mcp_io!()` macro skeleton, `config.rs` XDG helpers.
- **Success criteria:** `otto ci` green; a doctest expands `mcp_io!()` and reads back `server_key`/`bin`/`version`.

#### Phase 2: serve
**Model:** opus
- Production generic `serve<H>` (stdio lifecycle: `serve((stdin,stdout))` -> `waiting()` -> log quit reason). The logging-discipline helper that routes `log`/`tracing` to a file before serving, so the crate stays under `#![deny(clippy::print_stdout)]` with no stdout writes.
- **Success criteria (assertions, not process):**
  - a test drives the fake handler through `serve` and asserts a clean shutdown on client disconnect (`waiting()` returns, quit reason logged);
  - a test captures the crate's stdout during `serve` and asserts it contains ONLY JSON-RPC frames (no log lines).
- Testing discipline: at least one of these is verified by breaking the code and watching the test fail (per the tests-must-bite rule); that is a practice, not an acceptance criterion.

#### Phase 3: register / unregister / status
**Model:** opus
- Two mechanisms, one per target class:
  - Claude Code `user`/`project`: WRITES shell out to `claude mcp add-json <key> '<json>' -s user|project` (register) and `claude mcp remove <key> -s user|project` (unregister). This treats `~/.claude.json` as OPAQUE (no risk of dropping the user's other global keys), is idempotent, and copies the in-house proven pattern already used in Scott's `manifest.yml:46`. If the `claude` CLI is absent, fail loud with the exact command to run. `status` does NOT shell out: it reads the target config files directly (read-only presence detection of `mcpServers.<key>`), so it works even without the `claude` CLI on PATH.
  - `desktop`: no `claude` CLI in a Desktop-only install, so direct-write. Parse the file as `serde_json::Value`, splice ONLY `mcpServers.<key>`, preserve every other key, write atomically with `tempfile_in(target_dir)` (same-dir temp -> fsync -> rename; a `/tmp` temp fails EXDEV across partitions), preserve file permissions.
- `status` reports where the server is registered (which targets carry the key) and, for `serve`-readiness, whether the host's `get_info` name matches the bin (catches the `rmcp`-reports-itself gotcha).
- File-state edges, fail LOUD or fail SAFE (never silently overwrite):
  - missing / zero-byte file (slack-cli ships an empty `.mcp.json`) -> start fresh and write our key;
  - present but malformed JSON, or `mcpServers` present but NOT an object -> ERROR, leave the file untouched;
  - key already present with a different value -> replace by default (idempotent registration of THIS build); `--force` not needed since the value is derived from `current_exe()`;
  - concurrent lost-update (Claude Code rewrites between our read and write, desktop path only) -> accepted low risk, documented; atomic write prevents a TORN file, not a lost update.
- **Success criteria:**
  - register -> status -> unregister round-trip (per target);
  - desktop direct-write: a config pre-populated with two OTHER servers AND unrelated top-level keys asserts ALL of them survive register AND unregister (not just other servers);
  - a second register is a no-op (byte-identical file);
  - register against a malformed config, or a non-object `mcpServers`, errors and leaves the file byte-for-byte untouched;
  - the `claude mcp add-json` path is verified against a real invocation so `<bin> mcp register` and a hand `claude mcp add-json` produce the same entry.

#### Phase 4: slack-cli integration (first consumer)
**Model:** opus
- Add `mcp-io` git dep (tag) + `tokio` to slack-cli. Add `Mcp(mcp_io::McpCmd)` to `Command`, a `name()` arm, and the early-intercept in `main.rs` mirroring renew's `Update` arm (with a `bail!` arm in `lib.rs::dispatch`). Write `SlackMcpServer` (rmcp `#[tool_router]`) wrapping the `SlackApi` methods (`search_messages`, `conversations_history`, `conversations_replies`, `chat_post_message`, `conversations_info`, `users_info`, `users_conversations`, `conversations_open`, `auth_test`, `workspace`, `download_file`). Set `ServerInfo` name to `"slack"` explicitly (the rmcp-reports-itself gotcha).
- `SlackMcpServer` OWNS a cloned `Config` (`Config: Clone`, `config.rs:142`), so `H: 'static` holds and construction is TOKEN-FREE (no login needed for register/bundle).
- Per-call token, concurrency spelled out: `SlackTokenSource` is not `Clone` (`valet.rs:61`) and `SlackClient` owns its source (`client.rs:69`), so each tool call REBUILDS source + client via `valet::build_source(&config)` + `SlackClient::new(...)` INSIDE `spawn_blocking` (reqwest::blocking panics on the async runtime), under a short lock released before the blocking call. A 401 maps to a RECOVERABLE tool error (mirror persona's typed `AuthFailed`, `mcp.rs:117`), never a protocol error. No probe in the library; if slack wants a fail-fast hint it probes in `main.rs` before the runtime, like persona.
- **Success criteria:**
  - `slack mcp serve` handshakes with an MCP client and lists the slack tools;
  - `slack mcp register --target user` adds the entry (via `claude mcp add-json`) and Claude Code calls a slack tool live;
  - the existing sync commands (read/search/write/...) are unchanged: no tokio runtime is built unless the `Mcp` arm runs.

#### Phase 5: bundle (.mcpb)
**Model:** sonnet
- Generate `manifest.json` from the host handler's advertised tool list + `McpIo` metadata; package the `.mcpb` per the `modelcontextprotocol/mcpb` spec.
- **SHIPPED REORDER (disclosed):** the original plan ordered this AFTER Phase 4 so it could be smoke-tested against slack's REAL handler. Because Phase 4 lives in the `slack-cli` repo and is gated on this repo's v0.1.0 tag, the bundle logic was built in `mcp-io` FIRST (ahead of Phase 4) and unit-tested against a FAKE handler that advertises a known tool set. Tool enumeration is generic over any `ServerHandler` (an in-process handshake, since rmcp 2.1.0's `Peer::new` is `pub(crate)`), so it works for slack's handler unchanged. The against-slack smoke test rides with the Phase 4 cross-repo follow-on.
- **Success criteria (as shipped in `mcp-io`):** `<bin> mcp bundle` produces a `.mcpb` whose `manifest.json` validates against the checked-in mcpb v0.3 JSON schema; a smoke test asserts the manifest lists the same tool names the (fake) handler advertises. The slack-handler version of this test rides with Phase 4.

#### Phase 6: docs + the checked contract artifact
**Model:** sonnet
- README for `mcp-io` (integration guide like renew's), slack-cli README update, and the CONTRACT ARTIFACT: a checked-in golden fixture of the registration entry format + the target path-resolution table, with a test asserting the writers match it. This is what a future `mcp-io-py` must satisfy so it cannot drift the way okta-auth did.
- Bump slack-cli INSIDE the integration PR (no standalone bump branch).
- **Success criteria:** `otto ci` green in both repos; the golden fixture test fails if the entry shape changes without updating the fixture.

## Acceptance Criteria

- [ ] A host embeds `Mcp(mcp_io::McpCmd)`, writes one `#[tool_router]` handler, and gets serve + register + unregister + status + bundle with no other MCP scaffolding of its own.
- [ ] `slack mcp serve` exposes the slack tools to an MCP client, and `slack mcp register --target user` makes Claude Code call one live, end to end.
- [ ] The desktop direct-write path preserves ALL unrelated top-level keys AND other servers (proven by a test with both pre-existing), and register is idempotent (byte-identical on a second run).
- [ ] `serve` writes only JSON-RPC frames to stdout; all logging goes to the file target (asserted by capturing crate stdout).
- [ ] The registration entry shape is pinned by a checked golden fixture per target; changing it without updating the fixture fails CI.

## Alternatives Considered

### Alternative 1: Copy-paste the scaffolding per repo (status quo)
- **Description:** each CLI hand-writes serve/register/logging.
- **Cons:** four divergent copies already, four rmcp versions, nobody self-installs, no bundle.
- **Why not chosen:** this is the exact problem. Rejected.

### Alternative 2: A proc-macro that generates the whole MCP from the CLI
- **Description:** derive tools from clap commands automatically.
- **Cons:** heavy magic, hard to test, hides the tool surface, fights per-tool schemas/instructions.
- **Why not chosen:** "magic that can't be made predictable and tested gets ripped out." The host writing an explicit `#[tool_router]` is clearer and matches the fleet.

### Alternative 3: Remote HTTP transport in the shared library
- **Description:** one lib covers stdio AND streamable-http, absorbing marquee/persona-mcp-prod.
- **Cons:** pulls axum + OAuth discovery (RFC 9728) into the shared crate; remote MCPs have a real deploy story stdio does not.
- **Why not chosen:** scope. Recorded in the Addendum.

### Alternative 4: `install`/`uninstall` verb naming
- **Description:** name the config-writing verbs `install`/`uninstall`.
- **Cons:** `slack update` already installs the BINARY (via renew), so `slack mcp install` = install what? Cognitive dissonance.
- **Why not chosen:** `register`/`unregister` is literally true (it registers the server in a config). Settled 2026-07-09 (Scott); see Resolved Decisions.

## Technical Considerations

### Dependencies
- **Planned at design time:** `rmcp = 2.1.0`, `tokio`, `schemars`, `serde`/`serde_json`, `clap` (derive), `dirs`.
- **As shipped (v0.1.0 `Cargo.toml`), the drift is intentional and recorded here:**
  - `rmcp = 2.1.0` with features `server, macros, client` -- the `client` feature was added for Phase 5's in-process tool-enumeration handshake (rmcp's `Peer::new` is `pub(crate)`, so listing a handler's tools needs a real client on the other end of a duplex pipe).
  - runtime deps beyond the plan: `log` + `env_logger` (file-routed logging discipline, Phase 2), `thiserror` (lib error enum), `tempfile` (same-dir atomic write, Phase 3), `zip` (`.mcpb` packaging, Phase 5).
  - `tokio` (rt-multi-thread, io-std, macros), `schemars`, `serde`/`serde_json`, `clap` (derive), `dirs` as planned. `eyre` is dev-only (examples); `jsonschema` is dev-only (bundle manifest validation test).
- Host adds `mcp-io` by git dep + tag; private repo, so consuming CI needs the `CARGO_NET_GIT_FETCH_WITH_CLI` + `insteadOf` recipe already used for okta-auth-rs.

### Performance
- Irrelevant at this scale (a local stdio child). One caution carried from the rust rules: never hold a lock across `.await`; run blocking host work (slack's `reqwest::blocking`) under `spawn_blocking` / `block_in_place`, matching persona-cli.

### Security
- The library handles NO tokens. Host auth is unchanged (slack-cli: valet + okta-auth). The library does not probe; a missing/expired token surfaces as a recoverable per-call tool error, and the host may add its own fail-fast pre-runtime probe (persona's pattern).
- `register` on Claude Code targets delegates to `claude mcp add-json`, which treats the config as opaque (no key-dropping risk). The `desktop` direct-write path uses `serde_json::Value` read-modify-write that preserves every unrelated key, atomic `tempfile_in` write, and preserved permissions; a malformed or non-object target errors rather than overwriting.
- No secrets in the entry: there is no `env` block in v0.1.

### Testing Strategy
- Fakes, not mocks: a dummy `ServerHandler` for serve; a `TempDir` config for register/status. Break-a-test to prove bite. Golden fixture for the entry shape.
- Register tests assert preservation of pre-existing servers and idempotency (the two ways config-write clobbering shows up).

### Rollout Plan
- Ship order (blast radius): `mcp-io-rs` v0.1.0 tagged first -> slack-cli consumes it by tag and bumps inside the same integration PR. No slack-cli change lands before the tag exists.
- All install targets ship in v0.1. Claude Desktop config + `.mcpb` are primary (company is majority macOS); Claude Code user/project covers Linux (the minority); Windows is unsupported by choice. No official Claude Desktop on Linux, so `register --target desktop` on Linux hits the community-build path only.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `register` clobbers unrelated keys in `~/.claude.json` (the user's whole global state) | Med | High | Claude Code targets delegate to `claude mcp add-json` (opaque); desktop path is Value-preserving RMW; preserve-ALL-keys test |
| Host forgets `.with_server_info`, server reports as `rmcp` | Med | Low | library docs + a `status` warning when the handshake name != bin |
| `register --target desktop` on Linux finds no official app | Low | Low | company is majority macOS; doc that Linux Desktop is community-build only; Claude Code targets cover Linux |
| slack-cli's first async surface destabilizes sync commands | Low | Med | runtime built ONLY inside the `Mcp` arm; sync path untouched (AC asserts it) |
