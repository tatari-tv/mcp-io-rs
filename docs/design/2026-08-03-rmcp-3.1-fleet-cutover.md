# Design Document: rmcp 3.1 Fleet Cutover

**Author:** Scott Idler
**Date:** 2026-08-03
**Status:** In Progress (Phase 1 shipped as `v0.3.0`; scope widened 2026-08-04)
**Review Passes Completed:** 5/5, plus cross-model review panels on 2026-08-04
(design review, then an implementation audit of Phases 0-1)

## Summary

**Every rmcp use at Tatari goes to 3.1. No exceptions, no partials.** That is the
scope as of Scott's 2026-08-04 ruling, and it is wider than this doc's first four
revisions, which covered only `mcp-io` and its consumers.

`mcp-io` pinned rmcp 2.2; latest published is 3.1.0. rmcp is a PUBLIC dependency of
`mcp-io`, so bumping it is a breaking change for every consumer, and the consumers have
to move in lockstep or they cannot compile. For the five `mcp-io` repos that is a
dependency change plus a ship order, with ZERO source changes, and `mcp-io` itself has
already shipped (`v0.3.0`, commit `bdaff15`).

Two more targets were added on 2026-08-04, both measured rather than assumed:

- **`marquee/mcp`** (rmcp 1.8.0), previously an explicit Non-Goal. Probed: the whole
  marquee workspace compiles on 3.1 with **one** source line changed. The old exclusion
  rested on a cost estimate that turned out to be wrong.
- **`tatari-tv/platform-templates`** (rmcp **0.13**, six manifests), which no prior
  revision of this doc knew existed. This is the Backstage scaffolder that generates new
  Rust API services, so it is the one target whose staleness REGENERATES: fix the fleet
  and skip this, and the next `rust-api` service is born ~13 majors behind.

### How the inventory was wrong, and the search that fixes it

The first four revisions built their inventory with:

```
gh search code --owner tatari-tv 'mcp-io filename:Cargo.toml'
```

That searches for **`mcp-io`**, so it can only ever find rmcp users that depend on
`mcp-io`. It is structurally incapable of finding an rmcp user that does not, which is
exactly what `marquee/mcp` and `platform-templates` are. The doc even recorded the
lesson from its own earlier miss ("do not hand-maintain this list") and then repeated the
mistake one level up, by searching for the wrapper instead of the dependency.

The correct search, and the one this revision's inventory comes from:

```
gh search code --owner tatari-tv 'rmcp filename:Cargo.toml'
```

It returns 12 manifests across 6 repos: the five already known, plus
`platform-templates` (6 files) and `marquee/mcp`. **Search for the dependency you are
migrating, never for the wrapper you happen to own.**

## Problem Statement

### Background

- `mcp-io` 0.2.0 pins rmcp `2.2` twice: `Cargo.toml:15` (dep) and `Cargo.toml:28` (dev-dep).
- rmcp is a PUBLIC dependency, not an internal one:
  - `McpCmd::run` and the serve seam are generic over `rmcp::ServerHandler` (`src/cmd.rs:6`, `src/serve.rs:62,74`, `src/bundle.rs:7`, `src/register/mod.rs:8`)
  - `Error` boxes rmcp types (`src/error.rs:23,63,66`)
- FOUR repos consume `mcp-io` over a git tag, from
  `gh search code --owner tatari-tv 'mcp-io filename:Cargo.toml'`. Do not hand-maintain
  this list: the first draft said "three" because it enumerated from memory and missed
  `persona-cli`. **And do not trust this search for scope**, either: see "How the
  inventory was wrong" above. It finds `mcp-io` consumers, not rmcp users.

| consumer | mcp-io pin | own rmcp pin | resolves | tracked `Cargo.lock`? |
|---|---|---|---|---|
| `slack-cli/Cargo.toml:27,32` | `v0.1.4` | `2.1.0` | 2.2.0 | yes |
| `clyde/clyde/Cargo.toml:30` + `clyde/sessions/Cargo.toml:17` | `v0.1.2` | `2.1.0` | 2.2.0 | yes |
| `persona-cli/Cargo.toml:22,26` | `v0.1.2` | `2.1.0` | 2.2.0 | NO |
| `marquee/cli/Cargo.toml:28,32` | `v0.1.2` | `2.1.0` | 2.2.0 | yes |

- Nothing is split today: every consumer's `Cargo.lock` has exactly one rmcp, at 2.2.0.

#### The rmcp users that are NOT `mcp-io` consumers

These use rmcp directly and are invisible to the `mcp-io` search. Both are IN scope as of
2026-08-04. Neither is gated by the `mcp-io` tag, because neither depends on `mcp-io`.

| target | rmcp pin | how it uses rmcp | measured cost to 3.1 |
|---|---|---|---|
| `marquee/mcp/Cargo.toml:24` | `1.8.0` | hand-written `ServerHandler`, Streamable-HTTP server | **1 source line** |
| `platform-templates` skeletons `{actix,axum,rocket}/Cargo.toml` | `0.13` | generated service scaffold, `ServerHandler` + `tool_router` | 12 compiler errors in 1 shared file |

`platform-templates` is not a Rust repo at its root: it is a Backstage scaffolder driven by
`package.json` / `yarn`, with no cargo version of its own. The rmcp pin lives in three
skeleton manifests, the shared MCP source is ONE file
(`templates/services/rust-api/skeletons/mcp/src/mcp.rs`), and the three
`tests/golden/rust-api-*-mcp/` trees are GENERATED fixtures refreshed with
`node tests/harness/run.js --update` (`yarn test:golden`). So it is 3 manifests plus 1
source file plus a regenerate step, NOT 6 hand edits.

### Problem

A public-dependency major bump is breaking even when no source line changes. Proven,
not asserted: with `mcp-io` on rmcp 3.1 and `slack-cli` left on rmcp 2.2, `cargo check`
fails.

```
error[E0277]: the trait bound `SlackMcpServer: rmcp::handler::server::ServerHandler` is not satisfied
note: there are multiple different versions of crate `rmcp` in the dependency graph
   rmcp-3.1.0/src/handler/server.rs:593  this is the expected trait
   rmcp-2.2.0/src/handler/server.rs:432  this is the found trait
```

So the bump is not three independent chores. It is one ordered cutover: tag `mcp-io`
first, then each consumer repoints the tag AND bumps its own rmcp in the SAME commit.

### Why now

Be honest about the driver: this is maintenance, not a feature. No host we use requires
MCP 2026-07-28 today, and nothing is broken on 2.2. Two reasons it goes now anyway:

- **Scott asked for it**, 2026-08-03: the rmcp 3.1 change rides now rather than waiting for
  a `MCP-Protocol-Version: 2026-07-28` requirement from Claude.
- **The cost only rises.** Today it is a Cargo.toml edit, proven. A crate left behind long
  enough ends up multiple majors back with real migration work to do. That is what
  deferring buys.

### Goals

**The goal is total: after this doc, NO manifest at Tatari pins rmcp below 3.1.**
`gh search code --owner tatari-tv 'rmcp filename:Cargo.toml'` returns 12 manifests, and
every one of them reads 3.1 when this is done.

- `mcp-io` on rmcp 3.1, released under a tag consumers can pin. **DONE:** `v0.3.0`,
  commit `bdaff15`.
- `slack-cli`, `clyde`, `persona-cli` and `marquee/cli` on that tag with rmcp 3.1.
- `marquee/mcp` on rmcp 3.1, so `marquee`'s workspace lock resolves exactly ONE rmcp.
- `platform-templates`' three Rust API skeletons and their generated goldens on rmcp 3.1,
  so newly scaffolded services are born current instead of ~13 majors behind.
- EVERY in-scope repo resolves exactly one rmcp, at 3.1.0. **There is no longer any
  deliberate exception.** The previous revision carved out `marquee` on the grounds that
  `marquee/mcp/` stayed on 1.8.0; that carve-out is gone, and A2 now covers marquee.
- The MCP wire output does not change for clients negotiating a protocol below 2026-07-28.

## Proposed Solution

### Overview

For the `mcp-io` fleet: bump the dependency, nothing else. For the two direct rmcp users:
bump the dependency and fix what the compiler names, which is one line in `marquee/mcp`
and one file in `platform-templates`.

The probes below are the whole design argument. Every target is measured, none estimated.

EIGHT phases. Phase 0 is a zero-product-code spike; Phases 1-5 are one `mcp-io` consumer
each; Phases 6-7 are the direct rmcp users that no earlier revision covered.

| phase | repo to work in | gated by the tag? |
|---|---|---|
| 0 | local throwaway build of `clyde`, nothing committed | no |
| 1 | `tatari-tv/mcp-io-rs` (this repo) | it IS the tag |
| 2 | `tatari-tv/slack-cli` | yes |
| 3 | `tatari-tv/clyde` | yes |
| 4 | `tatari-tv/persona-cli` | yes |
| 5 | `tatari-tv/marquee`, the `cli` crate | yes |
| 6 | `tatari-tv/marquee`, the `mcp` crate | **no** |
| 7 | `tatari-tv/platform-templates` | **no** |

**Phases 5 and 6 are ONE commit in ONE worktree.** They are the same repo and share one
workspace `Cargo.lock`; splitting them would leave a commit whose lock carries two rmcp
majors for no reason. They are numbered separately only because they have different
rationales and different gating: Phase 5 waits on the `mcp-io` tag, Phase 6 does not.

**Phases 6 and 7 do NOT wait on Phase 1.** Neither target depends on `mcp-io`, so the
lockstep constraint does not apply to them. Phase 7 in particular can start immediately
and in parallel with everything else.

### The probe

Reproducible in a scratch dir. `git archive HEAD` each repo so the probe reads committed
state, edit ONLY Cargo.toml, then run clippy and the tests:

```bash
# mcp-io itself
git archive HEAD | tar -x -C "$P/probe"
cd "$P/probe" && sed -i 's/^rmcp = { version = "2.2"/rmcp = { version = "3.1"/' Cargo.toml
cargo clippy --all-targets -- -D warnings && cargo test

# a consumer: bump its rmcp AND point mcp-io at the local probe
sed -i "s|^mcp-io = .*|mcp-io = { path = \"$P/probe\" }|" Cargo.toml
sed -i 's|^rmcp = { version = "2.1.0"|rmcp = { version = "3.1"|' Cargo.toml
```

Do NOT put the probe on a tmpfs `/tmp`: three cargo target dirs ran a 16G tmpfs to 100%
full mid-run and the failure surfaces as a confusing `No space left on device` from
rustc, not as anything about rmcp. Use a disk-backed path.

The probe ran `--all-targets` while `otto check` runs `--all-targets --all-features`. That
is the same surface here: NONE of the manifests in play declares a `[features]`
table (`mcp-io-rs`, `slack-cli`, `persona-cli`, and clyde's root / `clyde` / `sessions`), so
`--all-features` is a no-op. Verified, so the probe is not narrower than CI.

**Known hole, stated rather than hidden: the probe used `mcp-io = { path = ... }` and never
exercised `tag = + version =` resolution.** Phases 2-5 change BOTH fields, and this doc
insists on both ("or cargo fails to resolve"), so the one mechanism that can still fail at
implementation time is exactly the one the probe skipped. Phase 0 shares the gap. Treat
resolving the git dep with both fields as the first thing each consumer phase proves, per
criterion A6.

What the probe DOES cover on that axis: consumers were pointed at mcp-io HEAD (`0.2.0`), not
at their currently-pinned `v0.1.2` / `v0.1.4`. So the mcp-io API delta between those tags
and the next one is covered, not merely the rmcp delta.

| target | edit | result |
|---|---|---|
| `mcp-io` `30a7af5` | rmcp `2.2` -> `3.1`, both entries | clippy clean; **45 unit + 1 integration + 1 doctest pass**, 0 failed |
| `slack-cli` `def7d27` | rmcp -> `3.1`, mcp-io -> probe path | clippy clean; **492 tests pass** |
| `clyde` `7ae3eba` | `sessions` rmcp -> `3.1`, `clyde` mcp-io -> probe path | clippy `--workspace` clean; all suites pass, 0 failed |
| `persona-cli` | rmcp -> `3.1`, mcp-io -> probe path | clippy clean; **254 tests pass** |
| `marquee/cli` | rmcp -> `3.1`, mcp-io -> probe path, `mcp/` LEFT on 1.8.0 | `cargo check -p marquee-cli --all-targets` clean; **129 tests pass** |
| negative: `slack-cli` rmcp `2.2` + `mcp-io` 3.1 | mismatched majors | `E0277`, as quoted above |

#### The 2026-08-04 probes for the two widened targets

Same recipe, `git archive HEAD` so committed state is what gets read, disk-backed scratch.
The `mcp-io` dep pointed at the REAL shipped tag (`tag = "v0.3.0", version = "0.3.0"`),
not a path override, so these two also discharge A6 for marquee.

| target | edit | result |
|---|---|---|
| `marquee` WHOLE workspace | `mcp/` rmcp `1.8.0` -> `3.1`, `cli/` rmcp `2.1.0` -> `3.1`, `cli/` mcp-io -> `v0.3.0` tag, plus ONE source line | `cargo check --workspace --all-targets` clean; clippy clean on `marquee-mcp` + `marquee-cli`; **170 tests pass**, 0 failed |
| `platform-templates` axum golden | rmcp `0.13` -> `3.1`, no source edits | **12 errors, ALL in `src/mcp.rs`** |

**`marquee/mcp` needs exactly one source line.** The only break was
`StreamableHttpServerConfig::with_stateful_mode`, which 3.1 renamed:

```
mcp/src/lib.rs:988   .with_stateful_mode(false)  ->  .with_legacy_session_mode(false)
```

The rename is deliberate upstream behavior tied to SEP-2567: sessions are removed at
protocol 2026-07-28, so the flag only governs legacy (`< 2026-07-28`) versions and was
renamed to say so (`rmcp-3.1.0/src/transport/streamable_http_server/tower.rs:60-72`,
builder at `:216`). **The `false` is load-bearing:** 3.1's `Default` sets
`legacy_session_mode: true` (`:164-176`), while marquee deliberately runs stateless behind
the shared gateway with `NeverSessionManager`. Dropping the argument would silently turn
sessions ON. The two neighbouring calls in the same chain, `with_json_response` and
`disable_allowed_hosts` (`:190`, `:221`), both still exist unchanged.

Everything else `marquee/mcp` touches survives 1.8 -> 3.1 untouched: `Extension`,
`Parameters`, `Json`, `ServerHandler`, `tool`/`tool_handler`/`tool_router`, `ErrorData`,
`ServerCapabilities`, `ServerInfo`, `ErrorCode::{INTERNAL_ERROR,INVALID_PARAMS}`,
`NeverSessionManager`, `StreamableHttpService`.

**`platform-templates` is the only real migration in this doc**, and it is bounded: 12
errors, all in the one shared file, all mechanical and all enumerated by the compiler.

| break | fix |
|---|---|
| `Content` not found (3 sites) | renamed to `ContentBlock` (`rmcp-3.1.0/src/model/content.rs:259`); no back-compat alias exists |
| `RawResource` not found (2 sites) | resource model reshaped in `src/model/resource.rs` |
| `PaginatedRequestParam`, `ReadResourceRequestParam` not found | request-param types moved/renamed |
| `ListResourcesResult` missing `cache_scope`, `result_type`, `ttl_ms` | new required fields |
| 4 sites: "cannot create non-exhaustive struct using struct expression" | use the constructors/builders instead of struct literals |

That last category is the one to watch: it is why this cannot be a `sed`. The rest is a
rename pass.

### Why nothing breaks

`mcp-io` has NO production `ServerHandler` impl; its public surface only takes one as a
bound. Five impls do exist, all in test modules (`src/cmd/tests.rs:12`,
`src/serve/tests.rs:13`, `src/bundle/tests.rs:37`, `src/register/tests.rs:18,23`), and the
probe showed those compile unchanged too. Say it that way: an earlier draft claimed
mcp-io "never implements `ServerHandler`", which is flatly false and was caught in review.
The conclusion survives the correction, because what drives migration cost is a
production impl and there is none.

Every rmcp item it names survives 2.2 -> 3.1 with a compatible shape: `QuitReason`,
`ServerInitializeError`, `ClientInitializeError`, `ServiceError`, `RunningService`,
`RoleClient`, `ServiceExt`, `IntoTransport`, `model::Tool`.

The one real signature change is `call_tool`:

| | 2.2 | 3.1 |
|---|---|---|
| `ServerHandler::call_tool` returns | `Result<CallToolResult, McpError>` | `Result<CallToolResponse, McpError>` |

`CallToolResponse` is an enum whose `Complete(CallToolResult)` variant carries the old
type (`rmcp-3.1.0/src/model/mrtr.rs:105-113`). Consumers are insulated twice over:

- `impl IntoCallToolResult for CallToolResult` (`src/handler/server/tool.rs:89`)
- `impl<T: IntoCallToolResult, E: IntoCallToolResult> IntoCallToolResult for Result<T, E>` (`:107`)

So `#[tool]` methods returning `Result<CallToolResult, McpError>` still compile, and
`#[tool_handler]` generates the converting `call_tool`. Both consumers use exactly that
shape (`slack-cli/src/mcp.rs:313,673`, `clyde/sessions/src/mcp.rs:197,485`).

**This is not a shim we own, and not a compatibility runway we are renting.** Three facts,
each read from the 3.1 source:

- Those `IntoCallToolResult` impls are rmcp's own code, not ours. There is no adapter in
  this repo to maintain or retire.
- `CallToolResult` is not the legacy type. It is the payload of
  `CallToolResponse::Complete`, the ordinary success case. The enum WIDENED the return to
  admit two additional outcomes; it did not replace the old one.
- Nothing on this path is deprecated. rmcp is explicit when it means legacy: `subscribe`
  and `unsubscribe` carry `#[deprecated]` with migration notes naming 2026-07-28
  (`src/handler/server.rs:432,442`). Neither `IntoCallToolResult for CallToolResult` nor
  `ServerHandler::initialize` carries one. The absence is a signal, not silence.

What we are declining is two new OUTCOMES, `InputRequired` and `Task`, which no tool of
ours needs. Not using a feature is not debt. `call_tool`'s own doc comment in 3.1 still
recommends `Ok(CallToolResult::error(...))` as "the right return value for almost every
'the tool didn't work' path", so returning `CallToolResult` IS the documented idiom.

### The wire does not change

Compilation proves types, not protocol. So the handshake was run for real, against the
`examples/spike.rs` server, on both versions:

```
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"spike-client","version":"0.0.0"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"ping","arguments":{}}}' \
  | cargo run -q --example spike 2>/dev/null
```

Output on rmcp 2.2 and on rmcp 3.1 is byte-for-byte identical, `md5 40e80ec22e610409bd519fd3df9b0089`:

```
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{}},"serverInfo":{"name":"spike","version":"0.2.0"},"instructions":"Phase 0 spike server. One tool: ping."}}
{"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"ping","description":"Trivial liveness check. Takes no parameters; returns the string \"pong\".","inputSchema":{"type":"object","properties":{}}}]}}
{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"pong"}],"isError":false}}
```

That buys three things:

- A 3.1 server still serves the LEGACY `initialize` + `notifications/initialized`
  lifecycle. The trait keeps `initialize` and adds `discover` with a default impl
  (`rmcp-3.1.0/src/handler/server.rs:318,343`). `initialize` is NOT deprecated and still
  performs version negotiation itself.
- Version negotiation is unchanged. `ProtocolVersion::KNOWN_VERSIONS` is the same
  five-element list in 2.2 and 3.1, and `LATEST` is `V_2025_11_25` in BOTH
  (`model.rs:170-186` in each).
- `CallToolResponse::Complete` serializes exactly as the old `CallToolResult`
  (`isError` + `content`), so no tool result changes shape.

**The byte-identical result is scoped to protocol < 2026-07-28, and that is deliberate
upstream behavior, not luck.** rmcp 3.1 carries BOTH lifecycles and picks one by
negotiated version (`src/service.rs:196-202`):

```rust
pub(crate) fn uses_legacy_lifecycle(protocol_version, uses_discover_lifecycle) -> bool {
    !uses_discover_lifecycle
        && protocol_version.is_none_or(|version| version < &ProtocolVersion::V_2026_07_28)
}
```

On the legacy path rmcp calls `strip_result_type_for_legacy_peer()`
(`src/model.rs:4597-4610`), which removes `resultType: "complete"` from the frame. That
is exactly why our 2.2-vs-3.1 diff was empty: the spike negotiated 2025-06-18.

**This is reachable TODAY, not eventually.** The default `supported_protocol_versions()`
returns `KNOWN_VERSIONS` (`handler/server.rs:339-341`), which includes `V_2026_07_28`
(`model.rs:181-187`). We do not narrow it. So any client that asks for 2026-07-28 gets it,
right now, the moment we ship 3.1. An earlier draft said "when a client eventually
negotiates", which understated it.

On that path, four things change, all automatic and none needing code from us:

- **Tool results gain `resultType: "complete"`.** The frames differ from the bytes recorded
  here. `strip_result_type_for_legacy_peer` covers list/read/prompt results too, not only
  tool calls (`model.rs:4597-4610`).
- **`ping` stops working.** At non-legacy it returns `method_not_found`
  (`handler/server.rs:112-116`). Note this is the MCP `ping` METHOD, not a tool named
  `ping`; the spike's `ping` is a tool invoked via `tools/call` and is unaffected.
- **A session can open with NO `initialize` at all.** `service/server.rs:529-541` accepts a
  non-initialize first request carrying valid 2026-07-28 `_meta` and calls
  `require_request_metadata()`. rmcp 2.2 hard-rejects that (`2.2.0/src/service/server.rs:223-227`).
  That is a new externally reachable server entry path, enabled by default. It is the
  biggest consequence of the gate and it is not a serialization detail.
- **`server/discover` answers by default**, returning `DiscoverResult::from_server_info(...)`
  (`handler/server.rs:339-351`) with a shape we have never characterized
  (`model.rs:1178`: `resultType`, `supportedVersions`, `ttlMs`, `cacheScope`).

Request `_meta` is NOT strictly required on the `initialize` path: `requires_request_metadata`

without `initialize` (`service/server.rs:541`). A reviewer claimed otherwise; it is wrong.

All of this means A3 is a version-scoped assertion rather than a universal one, and it is
written that way.

`tests/stdout.rs` independently confirms the legacy lifecycle: it drives a real

## Alternatives Considered

### Alternative 1: ship a tag for marquee only
- **Description:** change mcp-io for marquee's benefit alone, let the others follow whenever.
- **Pros:** smaller doc.
- **Cons:** leaves `slack-cli`, `clyde` and `persona-cli` on rmcp 2.x pinned to old tags, which
  is the split-majors asymmetry this doc exists to remove.
- **Why not chosen:** Scott's ruling above.

### Alternative 2: stay on rmcp 2.2
- **Description:** do nothing until a host demands MCP 2026-07-28.
- **Pros:** zero work, zero risk.
- **Cons:** the fleet drifts further behind and the eventual jump spans more majors.
  marquee's `mcp` crate is already two majors back at 1.8.0, which is what that costs.
- **Why not chosen:** the probe shows the bump is a dependency edit today. It gets more
  expensive by waiting, never less.

### Alternative 3: hold mcp-io at rmcp 2.2 and let consumers choose
- **Description:** keep `mcp-io` generic without pinning a major.
- **Pros:** consumers migrate on their own schedule.
- **Cons:** impossible. rmcp is a public dependency, and Cargo links two majors as two
  distinct crates with two distinct `ServerHandler` traits. `A5` is the proof.
- **Why not chosen:** not achievable in Cargo's model.

## Technical Considerations

### Dependencies

- rmcp -> `3.1` in ALL of: `mcp-io` (done), `slack-cli`, `clyde/sessions`, `persona-cli`
  (`Cargo.toml:26`), `marquee/cli` (`Cargo.toml:32`), `marquee/mcp` (`Cargo.toml:24`, from
  `1.8.0`), and `platform-templates`' three skeletons plus three generated goldens (from
  `0.13`).
- `mcp-io` git tag repointed in `slack-cli`, `clyde/clyde`, `persona-cli`
  (`Cargo.toml:22`) and `marquee/cli` (`Cargo.toml:28`). NOT in `marquee/mcp` or
  `platform-templates`: neither depends on `mcp-io`.
- **AMENDED TWICE on 2026-08-04.** First pass: the bullets listed only the three repos from
  the doc's first draft and were never updated when `542da55` and `7fc0a16` added the
  `persona-cli` and `marquee/cli` phases. Second pass: widened to the full rmcp inventory
  per Scott's ruling, adding `marquee/mcp` and `platform-templates`.
- rmcp feature sets are unchanged everywhere, and every feature still exists in 3.1:
  `mcp-io` uses `server, macros, client`; the four CLIs use `server, macros`;
  `marquee/mcp` uses `server, macros, transport-streamable-http-server,
  transport-streamable-http-server-session, tower, schemars`; the templates use
  `server, transport-streamable-http-server`. In 3.1 `client` gates `RoleClient` /
  `serve_client` (`rmcp-3.1.0/src/lib.rs:19-22`), which `mcp-io`'s bundle path needs and
  already enables.

### Performance

Not a factor. No hot path changes; the bump is a compile-time dependency edge.

### Security

- No new dependency surface adopted. rmcp's `auth` feature stays OFF in all six in-scope
  repos, `marquee/mcp` and `platform-templates` included.
- **`marquee/mcp` is the only in-scope crate that is externally reachable**, and Phase 6
  touches its session-mode flag, so it gets one specific check the others do not need:
  `legacy_session_mode` MUST stay `false`. 3.1 defaults it to `true`, so a dropped argument
  silently enables sessions on a gateway-fronted HTTP server. That is a behavior change on
  a network-facing surface, not a compile detail, which is why Phase 6's criteria assert the
  literal `with_legacy_session_mode(false)` rather than just "it compiles".
- Phase 7 changes what FUTURE services are born with. That makes it the highest-leverage
  security item in the doc: leaving the scaffolder on 0.13 means every new service starts
  ~13 majors of upstream fixes behind, and nobody reviews a template they did not write.
- `mcp-io-rs` is public with crates.io-only deps, so CI still needs no token. Do not
  introduce a private git dep into it: that would break the public CI path and reopen
  the clyde-clone problem that just closed.

### Testing Strategy

- Existing suites carry the load: 46 tests in `mcp-io`, 492 in `slack-cli`, the full
  `clyde` workspace. All pass on 3.1 already.
- `tests/stdout.rs` is the regression test for the protocol lifecycle: it drives a real
  legacy `initialize` and asserts only JSON-RPC frames reach stdout. It bites on 3.1.
- ADD one test in Phase 1 so this bug class cannot recur silently: assert the actual
  response frames for `initialize` / `tools/list` / `tools/call`, so a future rmcp bump
  that changes the wire fails CI instead of shipping. Today that guarantee is a one-off
  `md5sum` run by hand, which is exactly the kind of check that rots.
- Put that test in `tests/`, NOT in `examples/spike.rs`. The example is labelled
  throwaway in its own header and is not product code; a permanent CI guarantee must not
  hang off it. Mirror `tests/stdout.rs`, which already owns a real handshake against a
  handler and is the closest existing shape.
- **The test MUST pin `protocolVersion` explicitly below 2026-07-28**, the way
  `tests/stdout.rs:29` already pins `2025-06-18`. Without the pin, a future harness change
  that crosses the threshold makes the byte assertion fail for a reason having nothing to do
  with a regression, and the failure would read as "rmcp broke our wire" when it did not.
- Break it to prove it bites: change one byte of an expected frame and confirm the test
  fails.
- **What that test does NOT cover, named rather than implied (2026-08-04).** Both are
  acceptable because A3 is scoped to legacy happy-path frames, but neither should be
  discovered later as a surprise:
  - **Only the `< 2026-07-28` frame shape is guarded**, because `PROTOCOL_VERSION` is
    pinned at `2025-06-18` by design. The day a host negotiates 2026-07-28, this test
    asserts nothing about what that host sees. Confirmed reachable today: flipping the
    pin to `2026-07-28` makes rmcp 3.1 emit `resultType: "complete"` and the test fails
    naming that field, which is simultaneously proof the assertion bites and proof the
    coverage stops at the pin.
  - **Error frames are uncovered.** Only success payloads are asserted, so if rmcp
    reshapes the `isError: true` / error-content framing, the wire changes and this test
    still passes. Adding an error-path frame is the obvious next increment if the wire
    guarantee is ever widened past A3's scope.

### Rollout Plan

Phase 1 tag (SHIPPED) -> Phases 2-6 in any order. Phase 7 is independent of all of them and
can go first or concurrently.

Rollout differs by target, which the earlier "every one is a CLI" framing got wrong:

- **The four CLIs** (Phases 2-5): no runtime deploy. Rollout is `cargo install` on the
  developer machine plus each repo's normal release path.
- **`marquee/mcp`** (Phase 6): this one DOES deploy. It is a Streamable-HTTP server behind
  the shared gateway, so it follows marquee's normal service deploy and should be probed
  live afterwards (`sdv` / `verify` against the deployed version), not merely installed.
  This is the only phase where "done means live" involves a running service.
- **`platform-templates`** (Phase 7): nothing deploys and nothing installs. It lands on
  merge, and the verification is that a NEWLY generated service compiles. Rolling it out is
  the next `rust-api` scaffold anyone runs.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Claude Code's client cannot drive a 3.1 server | Low | High | Phase 0 spike, zero code, blocks everything. DISCHARGED: proven 2026-08-04 |
| A consumer lands the tag repoint and the rmcp bump in separate commits | Med | Low | One-commit rule in Phases 2-5; the broken commit fails CI immediately |

| rmcp 3.x tool JSON schemas shift via schemars | Low | Med | schemars stays 1.2.1 in the in-scope cargo repos; `tools/list` output verified identical |
