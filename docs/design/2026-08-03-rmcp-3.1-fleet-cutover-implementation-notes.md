# Implementation Notes: rmcp 3.1 Fleet Cutover

Running record for `docs/design/2026-08-03-rmcp-3.1-fleet-cutover.md`. Append-only:
a later decision that overrides an earlier one gets a NEW entry that supersedes it,
never a rewrite.

## Phase 0: prove a real host drives a 3.1 server

### Design decisions
- Probe built at `~/.cache/rmcp-spike`, NOT under `/tmp`. The doc warns that three
  cargo target dirs filled a 16G tmpfs; measured `/tmp` on `desk.lan` at the time of
  the run: `tmpfs 16G, 12G used, 4.5G available`. So the warning was live, not
  historical, and a `/tmp` build would have hit it.
- Drove the spike from a real Claude Code client via
  `claude -p --mcp-config <scratch.json> --strict-mcp-config`, with the server named
  `clydespike` so it could not collide with the live `clyde` entry.
- Exercised `clyde mcp register` / `status` against a scratch `CLAUDE_CONFIG_DIR`
  (`~/.cache/rmcp-spike/claude-config`), which the `--target user` help documents as
  honored. This runs the real `mcp-io` register code path, just not against
  `~/.claude.json`.

### Deviations
- **The doc's "register, restart Claude Code, call one tool, then re-register the
  INSTALLED clyde afterwards" sequence was NOT followed as written.** Two reasons,
  and the proof obtained is the same or better:
  - Restarting Claude Code would have ended the session executing the plan. A fresh
    `claude -p` subprocess is a real Claude Code client with a real MCP client, so it
    proves the same environmental assumption without that.
  - `--mcp-config` + `--strict-mcp-config` and a scratch `CLAUDE_CONFIG_DIR` mean
    Scott's live `~/.claude.json` was never written at all. Verified before and after:
    the live `mcpServers.clyde` entry is still `{"command":"clyde","args":["mcp","serve"]}`,
    the bare-name form, NOT rewritten to an absolute scratch path.
  - Consequence: the doc's re-register cleanup step became unnecessary rather than
    skipped. The residue it existed to remove was never created. Note that a literal
    `register --target user` WOULD have rewritten that entry to
    `current_exe()`, i.e. the throwaway binary, exactly as the doc warned.

### Tradeoffs
- Scratch-config proof vs. registering into live config: the literal reading exercises
  the exact bytes a real host reads at `~/.claude.json`, which is marginally closer to
  production. Rejected because it mutates live developer config mid-plan for no extra
  signal, and the failure mode if the plan aborted between register and re-register is
  a live MCP server pointing at a deleted scratch binary.
- `clyde` as the carrier (doc's choice, kept): `mcp-io` ships no binary, and clyde
  needs no Okta round-trip to start.

### Open questions
- None.

### Evidence
- Spike built clean against rmcp 3.1.0, zero source changes: only
  `mcp-io/Cargo.toml` (rmcp 2.2 -> 3.1) and `clyde/clyde/Cargo.toml` (mcp-io -> path
  override) plus `clyde/sessions/Cargo.toml` (rmcp 2.1.0 -> 3.1) were edited. Probe
  lock resolved exactly one rmcp, at `3.1.0`.
- Criterion 1 (tools listed, one `tools/call` returns): MET. The client saw
  `session_efficiency`, `session_grep`, `session_open`, `session_read`, `sessions_ls`,
  `sessions_search`, and `sessions_ls` with `limit: 2` returned 2 real session records.
- Criterion 2 (`clyde mcp status` names the server `clyde`, not `rmcp`): MET, asserted
  on OUTPUT not exit code, per the doc's warning that `status` exits 0 even on a name
  mismatch. Observed `clyde: user -> not registered` before and
  `clyde: user -> registered` after, with `register` printing
  `clyde: registered 'clyde' (user)`.

## Phase 1: mcp-io-rs to rmcp 3.1, tagged

### Design decisions
- Version moved via `cargo add rmcp@3.1 ...` for both the dep and the dev-dep, not by
  hand-editing `Cargo.toml`, per the house Rust rule against hand-edited versions.
  Confirmed `3.1.0` is genuinely latest with `cargo search rmcp` first.
- `tests/wire.rs` is its own integration binary with exactly ONE test, mirroring
  `tests/stdout.rs`. Both redirect the process's real fd 1; the libtest harness writes
  each test's `... ok` progress line to that same fd, so a sibling test finishing
  inside the capture window would corrupt the assertion. `tests/stdout.rs` documents
  this and the new file inherits the constraint.
- Frames are asserted as whole `serde_json::Value` objects rather than by field, so an
  ADDED field fails too. `resultType: "complete"` (what rmcp emits at protocol
  >= 2026-07-28) is precisely the regression class this must catch, and a
  field-by-field assertion would silently pass it.
- Server identity in the test is pinned to literals (`wire-test` / `0.0.0`), NOT
  `env!("CARGO_PKG_VERSION")`. A wire test must not need re-baselining every time the
  crate version moves. This is also the defect that broke the doc's md5 criterion.
- `serve_with` (the transport-generic core) is private, so the integration test drives
  the public `serve` over real fd 0/1. That is the better test anyway: it exercises
  the exact production path a host runs.

### Deviations
- **The doc's Phase 1 success criterion "the spike handshake md5 still equals
  `40e80ec22e610409bd519fd3df9b0089`" was AMENDED in the doc rather than satisfied.**
  It was broken two independent ways, neither fixable by any implementation choice:
  - It hashes an order-nondeterministic stream. rmcp dispatches each request as its
    own task, so the `tools/list` (id 2) and `tools/call` (id 3) responses race.
    Measured over 20 runs: `40e80ec22e610409bd519fd3df9b0089` (ids 1,2,3) 9 times,
    `076cf1054f725872a7e16c5574760977` (ids 1,3,2) 11 times. Identical content, only
    line order differs, so the criterion fails ~half the time for correct code.
    Piping through `sort` first is stable 10/10 and reproduces the recorded value
    exactly, so the recorded digest was right and the command was missing a `sort`.
  - The digest is crate-version sensitive and this phase's own `bump -m` changes it.
    `examples/spike.rs` reports `serverInfo.version` from `env!("CARGO_PKG_VERSION")`.
    Pre-bump (0.2.0) sorted digest `40e80ec22e610409bd519fd3df9b0089`; post-bump
    (0.3.0) `e29861f4e2950d5e7b73eada63ca9303`, stable 5/5, differing in exactly the
    one field `serverInfo: {"name":"spike","version":"0.3.0"}`.
  - Both amendments are recorded in the design doc next to the criteria they touch,
    with the command output. A3's conclusion is UNCHANGED: frame content really is
    identical across 2.2 and 3.1. Only the digest mechanism was unsound.
- `bump --no-tag -m` bumped `Cargo.toml` to 0.3.0 but its own `git add` failed with
  `.claude/hooks: can only add regular files, symbolic links or git-directories`. That
  is the known Claude Code sandbox phantom-file bug (bwrap deny-mounts leaking into
  the working dir), not a repo or `bump` defect. The version edit `bump` produced was
  correct and complete, so it was committed as `Bump version to v0.3.0`, matching the
  convention of the existing `8b58bcc "Bump version to v0.1.3"`. No version was
  hand-authored; the value came from `bump`.

### Tradeoffs
- Whole-frame `Value` equality vs. exact byte comparison: byte comparison would also
  catch key-order changes, but JSON key order here is a serde struct-field artifact
  with no protocol meaning, so it would generate false failures. `Value` equality
  still catches added, removed, renamed and changed fields, which is the actual
  guarantee. Chose `Value` equality.
- Matching responses by JSON-RPC `id` vs. by arrival position: position is simpler and
  was the first draft. It FAILED intermittently in `otto ci` (passed one run, failed
  the next, with `frames[1]` holding the id-3 response). Out-of-order responses are
  legal JSON-RPC and rmcp genuinely produces them, so `id` matching is correct
  semantics rather than a workaround. 25/25 clean after the change, and the flake was
  root-caused rather than retried.
- Keeping `examples/spike.rs` at all: its header claimed rmcp 2.1.0, which the bump
  made false. Corrected in place, with a note that the permanent wire guarantee lives
  in `tests/wire.rs` and not in an example its own header calls throwaway.

### Open questions
- None blocking. One observation for whoever ships Phases 2-5: the doc's per-repo gate
  table lists `marquee` in the ship-order diagram but omits it from the release-flow
  table (the table covers `mcp-io-rs`, `slack-cli`, `clyde`, `persona-cli`). Confirm
  marquee's gates live with `bump --gates` before its release step rather than
  inferring from the table.

### Evidence
- `rg -c '^rmcp = \{ version = "3.1"' Cargo.toml` returns `2`. A1 MET for this repo.
- `Cargo.lock` resolves exactly one rmcp, at `3.1.0`.
- `otto ci` exit 0, `All CI checks passed!`: 45 unit + 1 `stdout` + 1 `wire` + 1
  doctest, 0 failed.
- Source diff outside the new test: EMPTY of logic. Only `Cargo.toml`, `Cargo.lock`,
  the `examples/spike.rs` header comment, and README prose changed. The doc's
  "zero source changes" claim held.
- The wire test was broken twice to prove it bites: once on the `tools/call` text
  (`pong` -> `pang`) and once, after the `id`-matching rewrite, on the `tools/list`
  input schema. Both failed with the offending field named in the diff; both passed
  again on restore.

## Phase 1 addendum: A4's grep was fragile (found while walking criteria)

### Design decisions
- None beyond the amendment below.

### Deviations
- **A4 amended a second time, to anchor its pattern on `^mcp-io = `.** Walking the
  criteria after the phase commit showed each consumer manifest carries several
  git-tag deps, not just `mcp-io`. Measured: slack-cli `v0.1.4` / `v0.5.0` / `v0.3.3`,
  persona-cli `v0.1.2` / `v0.6.0` / `v0.3.3`, marquee/cli `v0.1.2` / `v0.5.0` /
  `v0.3.3`, clyde `v0.1.2` / `v0.3.3`. A4's bare `rg -c 'tag = "<phase-1-tag>"'` is
  safe for the actual Phase 1 tag (`v0.3.0`, which collides with nothing), so this did
  NOT block anything. But `v0.3.3` is three patch releases away and already sits in
  three of the four manifests; at that point the unanchored grep returns 2 and the
  criterion reads as satisfied by an unrelated dependency. Anchored rather than left
  as a trap for whoever runs Phases 2-5.

### Tradeoffs
- Could have left it alone since it is not wrong today. Rejected: the criterion is
  about to be run four more times by phases that have not started, and the failure
  mode is a SILENT false pass, which is the worst kind.

### Open questions
- None.
